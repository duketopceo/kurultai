# feat: v0.3.0 production unification — DB, backend, and unified UI

**Target repo:** `duketopceo/kurultai`
**Base:** `main@6c26115`
**Release tag:** `v0.3.0`
**Process:** swarm of scoped branches (`feat/v030-db-ingestion`, `feat/v030-backend-hardening`, `feat/v030-ui-rewrite`) → merge queue → PR → tag/release.

## Goal Capsule

Ship Kurultai `v0.3.0` to production with a production-grade DB ingestion layer, a hardened Rust backend, and a unified awe-inspiring Brain UI with light/dark mode.

- **DB + ingestion:** universal JSON/NDJSON ingestion, deterministic atom staging, schema v4 readiness, resilient embedding-dim handling, connector contract for future upload-ready sources, full test coverage.
- **Backend:** rewrite only where needed; focus on error propagation (`thiserror` typed errors, no silent `unwrap`/`expect` in fallible paths), debuggability (request IDs, structured spans), and Rust-level tests (`cargo test --locked`, `cargo clippy --all-targets -- -D warnings`, `RUSTFLAGS=-Dwarnings`).
- **UI:** rewrite `ui/` (embedded daemon UI) as a single, unified, awe-inspiring AI-brain surface. Deep black default with electric white/purple nodes; first-class light mode toggle. No parallel dashboards under `website/` or `web/`.
- **Team web app (`web/`):** keep in-scope for TypeScript build/lint and visual consistency, but do not require Clerk secrets for CI green. The app already degrades gracefully; v0.3.0 only needs build/time-invariance fixes.

**Stop when:** `cargo test --locked`, Rust clippy (`-D warnings`), and `web/` `npm run build` are green on the merged branch; the daemon serves the new UI at `/ui/`; a GitHub Release for `v0.3.0` exists; and residual findings are recorded in `docs/residual-review-findings/feat-v030-unification.md`.

**Do not:** change version to v1.0.0 (target is v0.3.0), create a second brain dashboard, commit secrets, or ship schema changes without a migration.

## Key Technical Decisions (settled-decisions brief)

### KTD1 — Three parallel branches merging in dependency order
- **Decision:** Run three isolated workstreams on `feat/v030-db-ingestion`, `feat/v030-backend-hardening`, `feat/v030-ui-rewrite`, then merge in the order DB → backend → UI.
- **Provenance:** Data-model changes (DB) must precede code that depends on them (backend), and UI last so it can use final shapes. User approved parallel agents + one large PR or sub PRs.
- **Rejected alternative:** One mega-branch. Rejected because concurrent agents need isolation; a single branch would conflict on `Cargo.lock` and large rewrites.

### KTD2 — SQLite remains primary store; JSON becomes a first-class connector
- **Decision:** Add `SourceKind::Json` and connector `src/connectors/json.rs` that reads JSON/NDJSON files from a configured path and maps records to `KnowledgeAtom` via a stable schema.
- **Provenance:** Current store already uses `sqlite-vec`; existing migrations exist; connectors trait lives in registry. JSON is the user’s requested upload format.
- **Rejected alternative:** New external database. Rejected as SQLite+vec matches current architecture and avoids ops overhead for v0.3.0.

### KTD3 — Schema change via numeric migration v006
- **Decision:** Add `ingestion_jobs` staging table and extend `knowledge_atoms` only through a new migration `MIGRATION_006`.
- **Provenance:** `migrations.rs` already uses sequential numeric migrations with `current >= CURRENT_SCHEMA_VERSION` (currently 5).
- **Rejected alternative:** Schema-free metadata columns. Rejected because staging needs strict provenance (batch_id, file_path, status, errors).

### KTD4 — Backend rewrite is surgical, not wholesale
- **Decision:** Fix error handling, add structured logging/request IDs, remove `unwrap`/`expect` in async connector/embed/http paths; no broad architectural change.
- **Provenance:** `src/store/mod.rs` is 1597 lines and uses `.map_err` heavily but still has panic-prone spots; `src/embed/mod.rs` retries but lacks request IDs.
- **Rejected alternative:** Rewriting `Store` trait or moving to SeaORM. Rejected: trait and SQLite layer work; scope must remain shippable.

### KTD5 — Single Brain UI surface, rewritten in vanilla JS/HTML/CSS
- **Decision:** Rewrite `ui/` only; keep the same Rust `rust-embed` delivery path (`ui::routes()`).
- **Provenance:** `AGENTS.md` warns against parallel dashboards and requires asking before visual changes; user authorized rewrite; light/dark mode requested.
- **Rejected alternative:** Building new `website/` dashboard or enhancing `web/` for brain view. Rejected per learned workspace facts.

### KTD6 — Three.js 3D graph with offline fallback
- **Decision:** Keep `3d-force-graph` + Three.js CDN by default; add a graceful static SVG fallback when `unpkg.com` is blocked (common in this environment).
- **Provenance:** AGENTS.md notes `unpkg.com` is blocked and canvas stays blank. Fallback must work without network.
- **Rejected alternative:** Bundling 3D libs into the Rust binary. Rejected because binary size and complexity; graceful fallback is sufficient.

### KTD7 — Release tag `v0.3.0`
- **Decision:** Tag `v0.3.0` only after all branches merge, tests pass, and GitHub Release created.
- **Provenance:** Current `Cargo.toml` version is `0.2.0`; user said "new V# release" and approved v0.3.0 during interview inference.
- **Rejected alternative:** `v1.0.0`. Rejected because this is a major feature release, not a stable 1.0 API commitment.
